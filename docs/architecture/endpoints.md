# Contratos HTTP actuales

Inventario de `backend/src/routes`, controladores, servicios y repositorios. Los prefijos se registran en `backend/src/app.js` (`/api`) y `backend/src/routes/index.js`. No introducir cambios de contrato durante la refactorización. Los campos opcionales no se marcan obligatorios salvo que el controlador/servicio actual lo compruebe explícitamente.

## Convenciones

- `JWT`: `Authorization: Bearer <token>`, validado por `validarJWT`.
- `Admin`: la cadena `requireAdmin` ejecuta primero `validarJWT` y acepta `rol_id` o `rol` numérico igual a `1` o `3`.
- Salvo respuesta binaria de archivo, las respuestas JSON de éxito incluyen `ok: true`; errores JSON incluyen `ok: false` y `mensaje`.
- La capa HTTP normalmente no valida esquemas formales: las validaciones enumeradas son las comprobaciones observables actuales.

## Notas sobre status y estabilidad

- `validarJWT` devuelve `401 {ok:false,mensaje:"Token no proporcionado"}` si no hay header y `401 {ok:false,mensaje:"Token inválido"}` cuando la verificación falla. El código actualmente toma el segundo elemento de `authorization.split(" ")`; no endurecer ese parseo en una refactorización de contratos.
- Registro y login traducen errores de servicio a `400`; no normalizar los códigos en esta etapa.
- `GET /api/health/` es público y actualmente el repositorio devuelve `ok`/fecha MySQL.
- Los mensajes en este documento conservan el texto del código fuente en UTF-8; el formato de respuesta y códigos documentados describen comportamiento actual, no una nueva especificación.
